# Refined implementation brief

Build and review the existing Engineering Studio flow using the current HTML/CSS/JavaScript frontend, a same-origin FastAPI API, SQLAlchemy, PostgreSQL in production, Argon2id, and Stripe-hosted subscription checkout. Use SQLite only for local development and isolated tests. Preserve the owner-private hosted frontend until production services and product terms are configured.

## Trust boundaries and acceptance criteria

1. **Identity**: A user account owns profiles, sessions, projects, subscriptions and notifications. User roles are `member` and `admin`; `free` and `premium` are derived subscription entitlements, not mutable roles. Never accept roles, prices, ownership IDs or entitlement claims from the browser.
2. **Authentication**: Hash passwords with Argon2id; require verified email; hash single-use verification/reset/MFA challenge tokens and enforce expirations. Use five-minute JWT access cookies and rotating, opaque 30-day refresh cookies. Check the database session, account status and authentication epoch on every authenticated API call. Revoke the session on refresh-token reuse and all sessions after password reset or logout-everywhere. Rotate CSRF tokens at authentication boundaries.
3. **Recovery and second factors**: Email delivery uses an encrypted transactional outbox and TLS SMTP worker. TOTP secrets are encrypted, codes reject replay, and recovery codes are hashed and consumed once. Google OIDC uses state, PKCE, nonce, signed ID-token validation and verified email; matching email does not silently link an existing account.
4. **Profiles**: Free allows one profile and Premium five. Enforce creation limits while holding an account-row lock. On downgrade retain all profiles and their projects, but authorize only the oldest allowed profiles. Profile switching and project reads/writes require ownership and current-plan eligibility.
5. **Authorization**: Deny protected frontend routes when server identity is absent. Treat frontend guards as UX only; enforce identity, ownership, current entitlement and admin role in API dependencies and handlers. Require MFA and a recent authentication for admin operations.
6. **Billing**: Select prices by server configuration. Persist a checkout-attempt idempotency key before contacting Stripe and reuse unfinished sessions. Existing subscriptions must use the billing portal. Verify webhook signatures over original bytes; persist each event atomically with its effects; re-read current provider state under an account lock to handle reordered events. A checkout return page never grants access.
7. **Lifecycle policy**: Active/trialing, recognized-price subscriptions grant Premium only until their recorded end time. Past-due/unpaid/incomplete/paused/canceled subscriptions do not grant access. Cancellation normally takes effect at period end. A full refund of the latest invoice suspends that period; partial refunds preserve access. Old-invoice refunds do not revoke a newly renewed period. Disputes suspend access pending operator review. Reconcile provider state regularly.
8. **Hardening**: Use strict request schemas, SQLAlchemy parameter binding, output escaping, same-origin CSRF validation plus signed cookie/header tokens, host allowlists, HTTPS, security headers, encrypted secrets at rest, persistent rate buckets, account lockout, audit records and device revocation. Bound request sizes at both the proxy and app.
9. **Operations**: Provide an admin view, currency-separated recorded revenue, bans, in-app/email notices, provider-managed promotions, optional once-per-account trials, account export and deletion. Pseudonymize deleted accounts while retaining only the records required by an operator-approved financial/security retention policy.
10. **Proof**: Include runnable integration tests, a schema migration, a dependency lock, a risk-to-fix review, deployment instructions and a release checklist. Do not claim production readiness from SQLite tests or mocked provider calls. Keep paid billing off by default until plan features, prices, provider eligibility and terms are approved.

## Explicit choices replacing ambiguities in the original prompt

- Preserve the current frontend instead of introducing an unrelated framework rewrite.
- Use opaque refresh tokens rather than refresh JWTs: refresh tokens require server-side rotation/revocation state anyway; opaque values expose fewer claims.
- Use Stripe for this implementation. Razorpay would require a separate provider adapter and event/lifecycle tests; the gateways are not interchangeable through a label change.
- Use provider-generated invoices and the provider billing portal rather than collecting payment information or inventing tax invoices.
- Keep profile quotas distinct from undefined premium engineering capabilities. A five-profile entitlement is implemented; additional paid features remain unspecified.
- Deploy the Python API on a compatible runtime. The existing static Sites deployment cannot run it. The same frontend detects the API only when served under that API's origin; static hosting continues to identify account/payment flows as previews.
